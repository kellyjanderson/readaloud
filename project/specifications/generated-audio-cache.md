## Scope

This specification defines local storage and reuse behavior for generated speech audio chunks.

## Backlink

Parent specification:

- [Imported Document Playback](imported-document-playback.md)

## Purpose

Once a chunk is generated, it should be reusable and should not be regenerated by default.

## Cache Layout

Generated audio must be stored under app-support storage using the following logical layout:

```text
generated-audio/
  {engineId}/
    {engineVersion}/
      {voiceId}/
        {rateKey}/
          {chunkHash}.wav
          {chunkHash}.json
```

The JSON sidecar must contain metadata required for validation and progress mapping.

`rateKey` format for `v1`:

- `rate_{(rate * 100).round().toString().padLeft(3, "0")}`

`chunkHash` format for `v1`:

- lowercase hex `sha256(cacheKey)`

## Required Metadata

Each cached chunk sidecar must include:

- `chunkId`
- `cacheKey`
- `engineId`
- `engineVersion`
- `voiceId`
- `rate`
- `normalizationVersion`
- `documentId`
- `segmentIds`
- `wordCount`
- `durationMillis`
- `createdAt`

## Cache Key Contract

`cacheKey` must include:

- engine id
- engine version
- voice id
- rate
- normalization version
- hash of normalized `speakText`

## Character Binding Identity

Voice and model identity come from the prepared character voice binding, including voice-asset digest, model-manifest digest, engine compatibility and pronunciation-profile identity. The cache key and sidecar must also identify effective pronunciation/delivery realization, adapter and boundary-policy versions. A stable voice name is insufficient when its bytes change. Binding revisions route result ownership; unchanged content fingerprints may reuse audio across revisions.

The runtime validates manifests and publishes assets/audio atomically. Legacy entries without required fingerprints are not reusable under the new contract. Characters reference shared manifests; they do not own cache files or native handles. Disk retention and cleanup remain shared cache-service responsibilities. This amendment does not introduce automatic eviction: any future disk-budget policy must preserve pinned queue/export audio and explicitly revise the retention contract below. See [Document Preparation and Execution Contexts](https://github.com/kellyjanderson/readaloud/issues/48).

## Retention Rules

- Generated chunk audio does not auto-expire.
- The app may offer manual cleanup controls later.
- Deleting a source document does not automatically delete generated chunk audio in `v1`.

## Invalidation Rules

Cached audio is invalid when any of the following changes:

- engine id
- engine version
- voice id
- rate
- normalization version
- normalized chunk text
- voice/model content fingerprint
- effective pronunciation/delivery realization and adapter/boundary-policy version

Invalid entries are ignored; they are not reused under a mismatched key.

## Startup Rules

- The app does not need to eagerly index the entire cache at startup.
- Cache discovery may be lazy by direct path lookup from `cacheKey`.
- If the sidecar is missing or malformed, the cached WAV is treated as invalid for reuse.

## Constraints

- Cache layout must remain platform-local and offline-friendly.
- Cache lookup must be possible by deterministic key without whole-cache indexing at startup.
- Reuse must remain safe under engine, voice, rate, and normalization changes.

## Acceptance

- Generated chunk audio can be reused without regeneration when the cache key matches.
- Invalid sidecars or mismatched keys safely prevent reuse.
- Cache retention aligns with the product decision to keep generated chunks until explicit cleanup.
