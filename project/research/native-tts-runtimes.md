## Why model support and bindings are separate questions

Apple's MLX Swift is a native API for MLX's numerical operations, including its Metal backend. The speech implementations layered on it still need model and tokenizer configuration, checkpoint loading, reference conditioning, the generation loop, and a matching audio codec. A Dart FFI call to a tensor operation only supplies the tensor operation. Binding a model-level Swift API or a compiled library can reuse all of those layers together. The app's existing Kokoro integration shows the pattern with a Dart caller, a Flutter plugin, and a native ONNX Runtime session executing the graph. [Apple MLX Swift](https://github.com/ml-explore/mlx-swift), [ONNX Runtime C API](https://onnxruntime.ai/docs/get-started/with-c.html), [Kokoro model runner](../../lib/src/services/kokoro_model_runner.dart)

## Binding options

| Option | Strength | Cost and evidence needed |
| --- | --- | --- |
| **Generated Dart/Swift bindings over Flutter platform channels** | A typed, asynchronous Dart API to a Swift plugin. Good fit for model operations, progress, and file-backed audio descriptors. | Swift must schedule inference away from the main thread and report results on the proper callback context. Pin the Pigeon generator to the project's Flutter/Dart toolchain and measure dispatch and packet overhead. [Pigeon](https://docs.flutter.dev/interop/pigeon), [channel threading](https://docs.flutter.dev/platform-integration/platform-channels#channels-and-platform-threading) |
| **Dart FFI to a narrow native C ABI** | A direct compiled binding with explicit buffer control. Appropriate if a proven library exposes C or profiling shows frequent buffer transfers dominate. | Define opaque handles, buffer owners, callback lifetime and cancellation. Run blocking native calls off the UI isolate. A Swift model library generally needs a stable C-compatible façade for this choice. [Flutter FFIgen](https://docs.flutter.dev/interop/ffigen) |
| **Supervised compiled helper** | Keeps hard termination, crash containment and a process-wide memory reclamation boundary while removing the interpreter. The Dart client can use a typed binding contract even if the Swift host delegates execution to the helper. | Has process startup, signing and supervision costs. Reuse the existing metadata/file protocol if a helper is needed. A model host crash or cancellation stall provides concrete evidence for this deployment rather than maintaining two paths by default. [Existing process ownership](../../lib/src/services/mlx_speech_worker_processor.dart) |

A runtime decision also requires checking all transitive deployment targets and licenses. Soniqo and Maralski declare macOS 15 in their reviewed manifests. The Neywa manifest declares macOS 14 and Swift tools 6.3. Those are package declarations. Confirm an actual build with the selected Xcode/Metal route and signed packaging. Keep package-code licenses, model/tokenizer/codec terms and packaged voice permissions separate. [Neywa package manifest](https://github.com/Neywa-Labs/mlx-audio-swift/blob/c7755e2504181a771941bb6f9f26ea79b3cdfce3/Package.swift), [Maralski package manifest](https://github.com/maralski/drama-tts/blob/dab788860de33569d50057bd20c4feed2c0227b1/Package.swift), [release compliance](../../docs/release-compliance.md)

## Separate native analysis question

ModernBookNLP's contract includes entity, coreference and speaker evidence attached to original source ranges. A transcription or synthesis SDK cannot supply that contract simply because it supports speech. A native replacement needs the same bounded-window and model-asset inventory, reconciled UTF-16 spans and a literary attribution comparison. A Kokoro/native-TTS release can still offer the current Dart heuristics without running the optional Python evaluator. Any removal of the offered evaluator needs a separate product decision. [ModernBookNLP capability assessment](modernbooknlp-capability-reuse.md), [provider setup and contract](../../docs/modernbooknlp-provider.md)
